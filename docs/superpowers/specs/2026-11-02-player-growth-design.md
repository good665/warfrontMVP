# 첫 플레이 안내·측정, 주간 공용 순위표·보상 설계

상태: 사용자 승인 완료(2026-11-02, “설계대로 순서대로 구현해줘”). 사용자 요청은 1단계 첫 플레이 안내와 측정, 2단계 미니게임 순위표와 시즌 보상, 이어서 검증이다.

## 목적과 범위

신규 사용자가 이동·공격·회피를 체력 소모 없이 익히고 첫 판을 완료하도록 안내한다. 안내 완료, 실제 게임 완료와 재도전, 매칭 대기·취소, 다음 날 재접속을 측정해 개선 근거를 만든다. 기존 주간 미니게임에 서버 검증 기록과 주간 순위 및 중복 지급 없는 보상을 추가한다.

진행 순서는 안내·측정 구현/검사 → 순위·보상 구현/검사 → 통합 Android 빌드와 가능한 실기기 검증이다. 기존 온라인 1:1/3:3, 주간 월요일 00:00 Asia/Seoul 순환, 무료 훈련과 45초 플레이를 유지한다.

활성 Unity는 `C:/Users/good6/WarfrontMVP/Assets/script`, 백엔드는 이 저장소 `backend/app`이다. 레거시 Unity 사본을 수정하지 않는다. 사용자 편집기의 저장하지 않은 장면을 덮어쓰거나 닫지 않는다.

운영 서비스 배포·스토어 제출·유료 상품·친구/길드·신규 미니게임·강제 푸시는 이번 범위에서 제외한다. 실제 iOS 기기와 추가 Android 기기가 없으면 해당 실기기 항목은 미검증으로 남기며 시뮬레이션과 구분한다.

## 고려한 접근과 제안

1. **기존 서버 확장 + 입력 재검산(추천):** 자체 이벤트 수집과 조회 도구를 만들고, 서버에서 발급한 실행 ID·시드·규칙 버전 및 입력을 재실행해 점수를 계산한다. 추가 외부 계정이 필요 없다. C#/Python 규칙 일치 검증이 필요하다.
2. **실시간 서버 미니게임:** 서버가 매 프레임 상태를 소유하고 클라이언트는 입력·표시만 한다. 재검산 엔진의 두 언어 유지 부담은 줄지만, 터치 사격과 기억 신호에 네트워크 지연과 연결 단절 처리가 직접 영향을 준다.
3. **외부 분석 서비스 + 별도 순위 서버:** 운영 분석 화면을 빨리 확보하지만 새로운 서비스 설정·데이터 전송·운영 의존성이 생긴다. 순위 점수 검증은 여전히 별도로 필요하다.

사용자는 기능 순서를 선택했다. 위 1번 기술 방식과 아래 기본값은 구현자의 제안이다. 상세 설계 승인 후 구현한다.

## 1단계: 첫 플레이 안내

- 계정별 안내 버전 `v1`과 진행 상태를 서버의 별도 테이블에 저장한다. 기존 Player 열을 변경하지 않아 기존 DB 레코드를 보존한다.
- 신규·기존 계정 모두 아직 v1을 완료하지 않았다면 처음 한 번 안내 진입점을 제공한다. 기존 사용자에게도 건너뛰기와 로비의 다시 연습하기를 제공한다. 안내를 건너뛴 사용자를 완료자로 집계하지 않는다.
- 환영 → 이동 목표 지점 도달 → 표적 공격 → 회피 → 완료 및 다음 목표 순서다. 실제 전투와 같은 조이스틱·공격·회피 버튼 위치와 입력 매핑을 재사용한다. 별도 무료 연습 상태를 쓰며 유료 경기 생성, 체력 소모, 재화 보상을 하지 않는다.
- 각 단계는 실제 조작 성공으로 진행한다. 단순 다음 버튼으로 조작 완료를 만들지 않는다. 건너뛰기는 언제든 가능하며 온라인 대전이나 로비 복귀를 막지 않는다.
- 앱 배경 전환은 정지한다. 종료 후 재실행하면 서버에 저장된 마지막 완료 단계에서 재개한다. 서버 기록 실패 시 로컬 진행을 보존하고 재전송하며, 안내 서버 장애로 게임 전체를 막지 않는다.
- 완료 후 무료 주간 훈련과 온라인 대전 진입점을 명확히 보여 준다. 첫 안내 완료 보상은 별도로 만들지 않는다.

## 이용기록 측정과 조회

- 분석 수집은 선택 사항으로 안내에서 동의를 받고 기본값은 비동의다. 로비 설정에서 변경할 수 있다. 안내 진행·순위·보상처럼 기능 제공에 필요한 상태 저장은 분석 이벤트와 분리한다. 동의하지 않아도 모든 게임을 이용한다.
- 자체 서버 이벤트 목록: 세션 시작, 안내 시작/단계/완료/건너뛰기, 모드 선택, 경기/훈련 시작·완료·재도전, 매칭 대기·취소·성공, 연결 실패와 복구. 각 이벤트는 enum 목록과 허용 필드만 받는다.
- 이벤트 ID로 중복 제거한다. 인증된 계정, 앱 세션, 실행 ID, 모드, 단계, 소요 시간, 성공 여부, 서버 수신 시각 정도만 저장한다. 이름·원시 기기 ID·인증 토큰·임의 문자열·터치 원본은 분석 이벤트에 넣지 않는다. 순위 검증용 입력 기록은 별도 데이터다.
- 클라이언트는 계정·서버별 최대 200개 이벤트를 7일 한도로 보관하고 최대 50개씩 전송한다. 성공 응답을 받은 ID만 제거한다. 제한된 재시도와 지수 지연을 사용한다. 동의 철회 시 보류 이벤트를 삭제하고 향후 수집을 중단한다. 서버도 동의 상태를 검증한다.
- 경기 정산과 서버 매칭 상태가 확인되는 항목은 서버에서 기록하고 실행 ID로 중복을 막는다. 클라이언트의 완료 보고를 분석의 유일한 근거로 쓰지 않는다. 안내·로컬 연습 성공은 조작 로그에 의한 클라이언트 보고이며 같은 신뢰 수준이라고 표현하지 않는다.
- 운영자는 `backend/tools/player_metrics.py --days 7` 같은 읽기 전용 명령으로 보고서를 확인한다. 공개 관리자 API나 클라이언트 내 관리자 키를 만들지 않는다.
- 보고서: 동의한 활성 계정 수, 안내 시작 대비 완료/건너뛰기, 첫 실제 판 완료율, 완료 후 재도전율, 모드별 완료율, 매칭 대기 중앙값·취소율, 다음 KST 날짜 재접속률. 안내 자체는 실제 첫 판에 포함하지 않는다. 미니게임·PvE·생존·온라인을 구분한다.
- D1은 첫 관측 KST 날짜의 다음 날짜 접속으로 정의한다. 아직 다음 날짜가 끝나지 않은 집단은 집계에서 제외한다. 수집 비동의 사용자 전체의 행동이라고 일반화하지 않으며, 이벤트 유실 가능성과 관측 표본 수를 표시한다.
- 검토에서 확인된 날짜 기준은 다음으로 고정한다(구현자 제안). 행동 지표의 기준 시각은 서버 수신/서버 확정 시각이다. 클라이언트 큐의 보류 여부·보류 경과를 함께 보내 지연 업로드를 별도 건수로 집계하고, 지연된 클라이언트 이벤트는 날짜별 전환율·D1에서 제외한다. 기기 시각으로 과거 접속일을 추정하지 않는다. D1은 온라인 세션 접속 확인을 기준으로 하며 오프라인 사용자의 실제 재방문률과 구분한다.
- 첫 판 완료율은 안내 완료/건너뛰기 최초 서버 관측을 기준으로 30분 안의 실제 게임 완료 계정 비율이다. 기준 후 30분이 지나지 않은 계정은 미성숙 집단으로 제외한다. 재도전율은 유효 완료 후 10분 안 같은 모드의 다른 실행을 시작한 비율이며 해당 10분이 지나지 않은 완료는 제외한다. 실행 ID로 연결하고 안내·개인 연습·공용 경쟁을 구분한다. 날짜별 집계는 기준 행동의 KST 수신일에 귀속하고, 서버 확정 게임 이벤트와 클라이언트 연습 이벤트를 분리해 표시한다.
- 원시 분석 기록은 30일 보관 후 명시적 정리 명령으로 삭제한다. 분석 조회에서 테스트 환경/계정을 분리한다. 새 외부 분석 SDK는 설치하지 않는다.

## 2단계: 공용 주간 순위표

- 기존 기기 최고 기록은 개인 연습 기록으로 유지한다. 이전 기록을 검증 없이 공용 순위나 보상 대상으로 올리지 않는다.
- 경쟁 기록은 서버가 실행 ID, 계정, 시즌, 종목, 규칙 버전, 시드, 시작 시각·만료 시각을 발급한 시점부터 만든다. 무료이며 계정당 동시 실행은 한 개다. 경쟁 시작 실패 시 개인 연습은 가능하지만 공용 기록으로 인정되지 않음을 표시한다.
- 모든 참가자는 해당 시즌 동일 시드를 사용해 표적·보급·암호 조건을 맞춘다. 재도전은 무료다. 규칙 버전은 주 도중 임의로 바꾸지 않는다.
- 클라이언트는 고정 시간 간격의 게임 진행과 양자화된 입력을 기록한다. 서버는 자신이 발급한 시드·규칙으로 동일 엔진을 재실행해 최종 점수를 계산한다. 제출 점수는 신뢰하지 않는다. 공용 순위 점수는 서버 응답값으로 표시한다.
- C#/Python의 차이를 피하도록 경쟁 규칙은 정수 좌표·명시적 PRNG·고정 틱을 사용한다. 세 게임의 정상·오답·충돌·연속 명중·종료를 공통 fixture로 비교한다. 기존 개인 연습도 동일 규칙 버전을 쓰되 저장 키를 버전별로 구분한다. 이전 로컬 최고 기록은 구버전 개인 기록으로 보존한다.
- 클라이언트 기록은 해당 틱의 동작만 허용한다. 시간 역행·중복/과다 동작·좌표 범위/비유한 값·허용 목록 밖 동작·과대한 입력 크기를 거부한다. 종목별 쿨다운과 속도는 서버 엔진 규칙으로 제한한다.
- 실행 완료를 서버에서 허용하기 전 실제 서버 경과 시간이 플레이 시간보다 짧으면 거부한다. 세션의 전체 벽시계 유효기간은 시작부터 10분이다. 일시정지는 그 안에서 가능하고 종료 시각을 넘기면 공용 기록은 인정하지 않는다. 재검산은 규칙 위반과 점수 조작을 줄이지만 자동 조작·변조 클라이언트를 완벽히 막는다고 주장하지 않는다.
- 제출은 실행별 1회 확정한다. 동일 요청 재전송은 같은 결과를 돌려주고 다른 내용으로 다시 확정하지 않는다. 타 계정 실행, 만료 실행, 불완전 입력, 다른 시즌/종목 제출은 거부한다. 취소·이탈은 보상과 공용 순위에 반영하지 않는다.
- 주간 최고 점수만 공용 기록으로 유지한다. 더 낮은 점수는 최고 기록을 덮지 않는다. 동점은 공동 순위(1, 1, 3 방식)이며 안정적인 표시 순서는 검증 시각·ID로 정한다. 공동 순위 보상도 같다.
- 현재 시즌 상위 50명과 내 순위·최고 점수·참가자 수를 표시한다. 미참가는 순위 없음으로 표시한다. 다른 계정의 내부 ID·입력 기록은 공개하지 않는다. 조회 실패 시 재시도와 로비 복귀를 제공한다.

## 시즌 마감과 보상 제안

- 월요일 00:00 새 시즌을 시작한다. 이전 시즌 직전 시작한 판의 제출을 최대 10분 허용하므로 이전 시즌 순위와 보상은 **월요일 00:10 KST 이후** 확정한다. 입력 제출은 시작+10분과 시즌 종료+10분 중 이른 시각까지다. 마감 뒤의 제출은 순위를 바꾸지 않는다.
- 종료한 시즌의 검증된 최고 점수가 0보다 큰 참가자를 대상으로 한다. 주간 등급 보상은 1위 다이아 30, 2~3위 20, 4~10위 10, 그 외 참가자 3개다. 한 계정은 해당 구간의 보상 하나만 받으며 중첩하지 않는다. 체력과 PvP 랭킹은 변경하지 않는다.
- 보상은 시즌 확정부터 28일간 수령 가능하다. UI에 마감/수령 기한과 보상 예정·확정·수령 완료를 구분한다. 현재 시즌 예상 순위 보상은 확정 보상으로 표시하지 않는다.
- 계정·시즌별 수령 UNIQUE 제약과 하나의 DB 트랜잭션으로 보상 기록 및 다이아 증가를 처리한다. 재시도·동시 요청·서버 재시작에도 추가 지급하지 않는다. 시즌·종목·순위·보상량은 서버가 결정한다.
- 순위 확정은 제출 마감 이후 조회·수령 시 안전하게 계산할 수 있게 한다. 별도 예약 작업이 없어도 월요일 마감이 적용되어야 한다. 완료/정산된 상태와 기록은 DB에 남겨 재시작 후 유지한다.
- 신규 테이블과 인덱스만 추가한다. 현재 운영 설정의 `AUTO_CREATE_TABLES=false` 환경을 위해 실행 가능한 명시적 스키마 적용 절차와 백업·복구 검사도 제공한다. 자동 스키마 생성에만 의존하지 않는다.

## 검증 기준

1. 안내의 실제 조작 단계, 건너뛰기·재개·재연습, 체력·재화 불변, 계정 분리, 수집 비동의 시 이벤트 미전송.
2. 이벤트 enum/크기/배치 제한, 인증, 동의 철회, 중복 ID·재전송, 오프라인 큐, 표본/날짜 경계·D1 미성숙 집단 제외와 조회 도구.
3. C#/Python 공통 기록 비교, 세 종목 점수 재검산, 변조·재전송·타 계정·만료·과다 입력·고속 종료 거부, 최고 기록 및 동점 순위.
4. 월요일 00:00과 00:10 경계, 진행 중 시즌 변경, 지난 시즌 조회, 보상 수령 기한, 중복·동시 요청·재시작 후 단 한 번 지급, 계정별 분리.
5. 기존 백엔드 및 Unity 검사 전체, 기존 온라인·무료 훈련 회귀, 새 DB 스키마 적용 전후 데이터 보존 검사.
6. Android 개발 APK 빌드 및 가능한 실제 기기에서 안내 → 첫 판 → 완료/재도전 → 주간 순위/보상·로비 흐름 확인. 다음 주차/시즌 마감은 검증 전용 시계·격리 DB로 검사하며 실제 보상 DB를 조작하지 않는다.
7. 다중 계정·동시 요청은 격리 서버에서 검증한다. HTTP 참가자와 실제 여러 사람의 기기 대전을 구분한다. iOS 실제 빌드/기기, 장시간 발열/FPS, 실제 운영 HTTPS 배포가 없으면 미검증으로 명시한다.

## 구현자에게 맡기는 세부 사항

기존 코드 스타일에 맞는 파일 분리, 화면의 세부 간격·색상, PRNG/고정 틱 정수 스케일, 입력 한도와 재시도 상한의 구체 값, SQL 인덱스·스키마 적용 도구 형식은 구현자가 검사와 문서로 결정한다. 점수 규칙 변경 시 버전과 개인 기록 표시는 일치해야 한다. 추적 데이터나 보상 트랜잭션을 구현하기 전 위 신뢰 경계부터 테스트한다.

## 구현 보충: 분석 코호트 기준과 원시 기록 보관

- 동의한 계정의 지연 없는 클라이언트 이벤트를 실제 서버에서 처음 수신할 때, 별도 ExperienceState에 `first_session_at`(최초 세션 관측), `first_guide_exit_at`(최초 안내 완료 또는 건너뛰기 관측) 두 시각만 저장한다. Player 필드는 변경하지 않는다. 이 최소 코호트 메타데이터는 원시 이벤트의 30일 보관·명시적 삭제 이후에도 유지하여, 기존 사용자가 새로운 D1 또는 첫 판 코호트로 재분류되지 않게 한다. 수집 비동의·지연 업로드는 최초 기준을 만들지 않는다. 과거 기준 메타데이터가 없는 기록은 관측 시작이 불명확한 left-censored 표본으로 표시하고 최초 코호트 분모에서 제외한다. 보고서는 읽기 전용이며 기준 시각을 추정하거나 보정 저장하지 않는다.
- 모드별 완료율은 시작이 보고 기간 안에 있고 시작 후 30분 전체가 경과한 실행을 분모로 삼는다. 같은 계정·출처·모드·실행 ID의 완료가 시작부터 30분 이내에 있어야 분자에 포함한다. 경계 시각은 포함하고, 실행 ID가 같은 중복 이벤트는 한 번만 센다. 클라이언트 개인 연습과 서버 확정 경기는 별도 비율이며 안내는 제외한다. 원시 시작·완료 건수와 성숙 실행 완료율을 함께 표시한다.
- `daily_cohorts_kst`는 첫 판 전환을 최초 안내 종료일, 재도전을 완료일, D1을 최초 세션 관측일의 KST 날짜에 귀속하며 각 분모·분자·비율과 출처별 전환을 제공한다. 날짜가 바뀐 뒤 일어난 전환도 기준 행동일의 분자에 반영한다. `daily_kst`의 수신일별 원시 이벤트 건수와는 별도 지표이다.
